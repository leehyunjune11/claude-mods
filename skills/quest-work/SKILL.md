# quest-work — 퀘스트 병렬 작업

입력: 퀘스트 id 목록 (예: `client-deck, contract-reply`). id가 없으면 어떤 퀘스트를 할지 먼저 묻는다.

## 절대 규칙

- **메일을 보내지 않는다.** 메일은 초안(임시보관함)까지만. 발송·전달·답장 보내기 도구는 쓰지 않는다.
- **퀘스트를 완료(done) 처리하지 않는다.** 체크는 사람이 한다.
- 캘린더 초대 수락, 일정 변경, 파일 수정·삭제처럼 바깥에 영향을 주는 행동은 하지 않는다. 읽기만 한다.

## 순서

1. `~/.quest/tasks.json`을 읽어 받은 id의 퀘스트(`t` 제목, `d` 설명, `due`)를 꺼낸다. 없는 id는 건너뛰고 알린다.
2. 각 퀘스트에 `"work": {"status":"running","note":"작업 중"}`을 써 둔다 (패널에 ⏳ 표시). 파일을 쓸 때는 매번 다시 읽은 최신본 위에 `work` 필드만 바꾼다 — 사람이 그 사이 체크한 것을 덮어쓰지 않게.
3. 지금 대화에서 알고 있는 관련 사실(상대 창구, 회신 규칙, 금액·일정 이력, 메모리 등)을 퀘스트별로 뽑아 둔다. 서브에이전트는 이걸 못 보니 프롬프트에 넣어 준다.
4. **퀘스트 하나당 서브에이전트 하나**를 `Agent` 도구(general-purpose)로 띄운다. 한 메시지에 여러 개를 동시에 띄워 병렬로 돌린다(최대 5개, 넘으면 5개씩 끊어서).
5. 결과가 오면 퀘스트마다 `work`를 갱신한다:
   - 초안을 만들었으면 `{"status":"ready","draft":true,"note":"<한 줄: 누구에게 무슨 답장>"}`
   - 자료만 정리했으면 `{"status":"ready","note":"<한 줄: 찾은 것과 다음 할 일>"}`
   - 사람이 직접 해야 하면 `{"status":"skip","note":"<왜>"}`
   - 실패면 `{"status":"failed","note":"<이유>"}`
   `at`에는 오늘 날짜(YYYY-MM-DD).
6. 대화창에 퀘스트별 결과를 정리한다: 무엇을 했는지, 초안 제목·수신자, 근거 자료(어디서 나온 내용인지 + 핵심 원문 인용), 사람이 확인할 점.

## 서브에이전트 프롬프트 (퀘스트마다 채워서)

```
너는 사용자의 업무를 돕는다. 아래 퀘스트 하나만 처리한다. 오늘은 <YYYY-MM-DD>.

퀘스트: <t>
설명: <d>
마감: <due 또는 없음>
관련 메모: <3단계에서 뽑은 사실>

1. 맥락 찾기 (읽기만). 연결된 도구만 쓴다 — 없는 건 건너뛴다. 도구가 deferred면 ToolSearch로 먼저 로드한다.
   - 메일(Gmail 등): 관련 스레드를 찾아 최근 대화와 첨부를 확인한다.
   - 드라이브·문서(Google Drive 등): 관련 문서·시트를 찾아 읽는다.
   - 캘린더: 관련 일정과 겹치는 일정을 확인한다.
   - 로컬 노트: 사용자가 알려 둔 노트 폴더가 있으면 grep/find로 찾는다.
2. 메일 답장이 필요한 퀘스트면 해당 스레드에 답장 초안을 만든다.
   - 받는 사람·참조는 원 스레드를 따른다.
   - 존댓말, 짧고 구체적으로. 모르는 사실(금액·일정)은 지어내지 말고 [확인 필요]로 남긴다.
   - 절대 보내지 않는다.
3. 메일이 아니면 찾은 자료로 다음 할 일을 정리한다. 파일·일정은 수정하지 않는다.

마지막에 이 형식으로만 보고한다:
- 결과: draft | context | skip | failed
- 한 줄 요약: (패널에 보일 문장, 40자 안팎)
- 초안: 제목 / 받는 사람 / 참조 (만들었으면)
- 근거: 출처(메일 제목·날짜, 파일 경로·링크)와 핵심 원문 인용
- 확인할 점: 사람이 보내기 전에 봐야 할 것
```
